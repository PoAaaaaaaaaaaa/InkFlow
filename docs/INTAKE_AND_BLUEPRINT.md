# 建作流程（v1.4.0）

四个功能：**建作前提问 → 蓝图展开与观览 → 声纹参照 → 写作深度控制**。

它们是一条链：问答产出的答案决定蓝图准不准，蓝图解出的深度决定正文怎么落笔，
声纹给正文提供类型级的节奏校准。

---

## 一、建作前提问（需求 1）

### 两层结构

```
作者填写内容
    ↓
① 本地规则扫描（IntakeQuestionnaire.localQuestions）—— 纯本地，零延迟，永不下线
    ↓
② AI 语义追问（AgentPipeline.generateIntakeQuestions）—— 补充题材特有问题
    ↓
IntakeQuestionnaire.build() 合并去重
```

**为什么本地规则是主干而不是兜底**：用户刚建作品时最可能的状态就是「还没配模型」。
如果提问靠 AI，离线用户整个流程就断了。所以规则层负责必需缺口，AI 层只做增量。

### 检测的是语义维度，不是字段空白

用户写了 200 字核心设定，全在讲世界观，一个字没提主角是谁——
这比字段为空更需要追问。所以检测落在语义上：

| 维度 | 检测方式 |
|---|---|
| 主角 | 关键词 + 中文人名模式（`叫|名叫|名为` + 2-3 字 + 标点） |
| 核心矛盾 | 冲突类关键词（对手/对抗/追杀/复仇…） |
| 金手指 | 题材相关，现实题材自动跳过 |
| 世界观规则 | 境界/体系/规则 + 代价/限制 |
| 结局方向 | 终将/登顶/牺牲… |
| 节奏偏好 | 快节奏/慢热/铺垫/爽点 |

### 优先级

- **1 必答**：不问就写不出可用大纲（主角、冲突、字数）
- **2 建议**：显著影响质量（金手指、结局、基调、世界规则、节奏）
- **3 可选**：锦上添花（关系线、禁忌）

必答题答完才允许进入下一步（`IntakeSession.readyForBlueprint`）。

### 每个问题都带「为什么要问」

这一条不能省。作者知道「答这题影响什么」才会认真答，否则一律跳过。
单元测试强制检查每条 `why` 非空且长度 ≥ 15。

## 二、蓝图展开与观览（需求 2）

### 结构由代码算，内容由模型填

**这是本模块最重要的设计决定。**

让模型「按 100 万字规划分卷」，实测输出从 12 卷到 400 章都出现过，
而且经常自相矛盾（说每卷 30 章，列出来 47 章）。

所以：结构是算术问题 → 归代码；模型只负责往结构里填内容。

```kotlin
// BlueprintStructure.of()  —— 纯算术，零 token
目标字数 ÷ 单章字数 = 总章数
总章数 ÷ 30 = 卷数
```

### 卷数的算法演进（踩过的坑）

第一版用分档表（≤200 章→5 卷、≤400 章→8 卷…），在 400 万字上崩了：
算出 **16 卷 × 84 章/卷**。单卷塞 84 章，无论从「一卷一个完整叙事弧」
还是读者的阅读耐心看都不成立。分档表的毛病是只保证档内正确，跨档就失控。

改用连续公式后，全区间落在 25–45 章/卷：

| 目标字数 | 章数 | 卷数 | 章/卷 |
|---|---|---|---|
| 20 万 | 67 | 2 | 34 |
| 100 万 | 334 | 11 | 31 |
| 300 万 | 1000 | 33 | 31 |
| 500 万 | 1667 | 56 | 30 |

### 生成流程

```
1. 解析深度档（DepthResolver）——不消耗 token
2. 计算结构参数（BlueprintStructure）——不消耗 token
3. 世界观设定   8-14 条
4. 角色         4-8 位
5. 伏笔         5-10 条
6. 分卷壳       卷标题 + 功能 + 梗概
7. 逐卷展开     每卷一次调用，产出该卷全部章节细纲
```

第 7 步是逐卷进行的，因为一次性生成 300 章细纲会远超输出长度限制，
而且模型在长输出后半段的质量会明显下降。逐卷展开还让进度可报告。

### 降级保证

每一步都用 `runCatching` 包裹，失败则该部分为空，**流程继续**。

引擎完全坏掉时（所有调用返回 `{}`），产出是：
- 结构完整：卷数、章数、序号连续，全部正确
- 内容缺失：章节标题是「第 N 章」，标记为「细纲待生成」

这比整体失败好：用户可以先用骨架，之后在写作台逐章补细纲。

### 章节连续性是硬约束

`fillMissingOrders()` 保证 `1..chapterCount` 无缺口。模型漏章时补占位——
宁可有骨架，不能断号。单元测试断言 `orders == (1..total).toList()`。

### 观览页

生成完成后全屏展示，四个标签：概览 / 世界观 / 角色 / 细纲。

**不直接入库**——一份百万字蓝图是 300+ 章细纲，作者不可能在对话框里逐条确认，
但也不能让它悄悄落库。规划是作品的地基，改地基要当事人点头（同 ADR-5）。

确认后：
- 分卷与章节**追加**，不删除已有内容（作者可能已经手写了几章）
- 世界观/角色/伏笔按 id 去重写入
- 蓝图解出的深度**同步进设置**，后续生成立刻按新档位走

## 三、声纹参照（需求 3）

### 边界，写在最前面

五本长篇合计**超过一千万字**。这个量级：

- 装不进任何模型的上下文（百万 token 级别也装不下）
- 不该进 APK（体积与版权双重问题）
- 就算装进去也没用——模型从一千万字里学不到「该怎么写这一章」

**真正可迁移的是可测量的特征**：句子呼吸长度、对话占比、标点习惯、用词层级。
提取出来只有几百字节，可以完整注入提示词，且能逐条检查、逐条调参。

需要逐句级参照时，正确路径是把原文导入为检索语料，让 RAG 按需召回——
那是检索问题，不是提示词问题。

### 提取的指标

| 维度 | 指标 |
|---|---|
| 节奏 | 平均句长、句长标准差、短句占比、**超短句占比**（≤6 字）、长句占比 |
| 段落 | 平均段长、对话行占比、每段句数 |
| 标点 | 每千字 感叹号/问号/省略号/破折号 |
| 用词 | 比喻密度、口语化程度、心理描写占比 |

### 口语化度量的修正（重要）

第一版用「的/了/呢/吧/啊」的合计密度，**实测结果反了**：书面语得分比口语高。

原因：书面语里「的」字定语结构极多（「属于他的、如今却已然易主的广袤土地」），
而口语短句里虚词反而少。**虚词密度衡量的是偏正结构密度，不是口语化。**

改用三个独立信号合成（单元测试抓出来的 bug）：

```
口语化 = 语气助词密度(40分) + 短句占比(40分) + 对话行占比(20分)
         ↑ 呢/吧/啊/嘛/哦/呀/哈/啦/嗯/唉/哟/咯 —— 几乎只出现在口语里
```

### 数据诚实：样本量必须标注

内置五条声纹来自**公开可查的作品简介与标签**，样本量只有几百字，
因此 `isReliable` 大多为 `false`，UI 上明确显示「样本量不足，方向性参考」。

这是刻意的：拿几百字简介冒充「已学习全书」是欺骗。
它们的作用是给出题材级的方向感，而不是精确对齐节奏数值。

要基于全文建立高保真声纹，走 `VoiceLibrary.extract()` 导入自己的文本，
得到 `isReliable = true` 的可靠声纹。

### 声纹混合

`VoiceLibrary.blend()` 按样本量加权平均。样本量大的作品自然权重更高——
这是它应得的，不是人为设置。

### 与深度的一致性校验

声纹的平均句长必须与深度谱系的目标句长一致，否则两条指令会互相打架——
模型收到「平均句长 14 字」和「平均句长 30 字」两份要求，只会随机挑一个。

`bestMatchFor()` 按句长距离排序（题材相同额外加权），选出匹配当前深度的声纹。
提示词里还显式声明冲突时的优先级：

```
① 作者文风 DNA > ② 写作深度 > ③ 同类作品声纹
```

这条不写清楚，模型会在三份矛盾的节奏指令之间随机摇摆。

## 四、写作深度控制（需求 4）

### 「深度」为什么不能是一个形容词

「写得深一点」是写作指导里最没用的一句话。模型对此的响应完全不可预测：
它可能加形容词堆砌、加比喻、加抒情段——**恰好全是最容易变成 AI 腔的东西**。

有效的深度控制必须**逐维度给可执行指令**。八个维度全部可判定：

| 维度 | 通俗向（level 10） | 深度向（level 90） |
|---|---|---|
| 目标句长 | 14 字，超 30 字每章 ≤5 处 | 32 字，长句是主要工具 |
| 目标段落 | 62 字，一个动作独立成段 | 145 字，可承载完整心理过程 |
| 比喻密度 | ≤1.5/千字，几乎不用 | ≤8.7/千字，可承担结构功能 |
| 心理描写 | 8%，情绪必须外化成动作 | 46%，内心活动即情节 |
| 专业术语 | ≤2/千字，必须跟白话解释 | ≤14.8/千字，不设限 |
| 类比讲解 | **需要** —— 出现概念当场解释 | **不需要** —— 相信读者 |
| 留白 | **不允许** —— 每件事交代清楚 | **允许** —— 动机可以不写明 |

### 具名档 + 连续滑块

作者说不清「深度 62 分」，但立刻能判断自己写的是「爽文」还是「文学向」。
所以两者都给：具名档是给人用的接口，数值是给模型用的参数。

| 档位 | level | 一句话 |
|---|---|---|
| 纯爽文 | 10 | 一句话能讲清的信息，绝不写两句话 |
| 通俗 | 32 | 大众阅读舒适区，不追求回味 |
| 平衡 | 55 | 网文主流的厚度 |
| 有厚度 | 76 | 人物动机要写到第二层 |
| 文学向 | 92 | 形式本身参与表意 |

**深度不等于好坏**。纯爽文不是低配版，它有自己的一套明确要求
（节奏压制、信息直给、零留白），照着写出来的是合格的爽文。
把文学向的规则套给爽文只会两头不讨好。

### 从问答推导

```
推断基线（题材 + 基调 + 受众）
    ↓ 覆盖
节奏偏好 ±18   ← 最强信号
基调补充 ±15
结局方向 ±10
可读性表态 ±25  ← 明确说「通俗易懂」时给最强信号
    ↓
clamp 到 5..95
```

三层兜底：问答答案 → 题材推断 → 平衡档。任何输入都有合理输出。

### 注入位置

| 场景 | 注入内容 |
|---|---|
| 生成整章 | 三层语料库 + 节奏校准（深度 + 声纹）+ 文风 DNA |
| 智能续写 | 选词 + 禁忌清单 + 节奏校准 |
| 润色 | **本文实际命中**的套话 + 选词 + 深度块 |

润色是深度控制最有效的位置：结构已经写好，只需要调文字的松紧。

## 五、验证状态

| 项目 | 结果 |
|---|---|
| core 单元测试 | ✅ 176/176 通过（新增 51 条覆盖这四项功能） |
| app 层 Kotlin 编译 | ✅ 通过（含 R 资源生成 + KSP） |
| APK 打包 | ⏳ 需 x86_64 云端 runner（aapt2 限制，同 ADR-7） |

### 测试覆盖的边界情况

- **本地提问在引擎坏掉时必须照常返回**（AI 返回非 JSON 的引擎）
- **蓝图在引擎全坏时结构仍必须完整**（所有调用返回 `{}`）
- **章节序号无缺口**（断言 `orders == (1..total)`）
- **伏笔回收不早于埋设 +3**
- **深度值域 clamp**（极端输入仍落在 5..95）
- **短样本声纹标记为不可靠**
- **口语法能区分两类文本**（就是这条测试抓出的度量错误）

## 六、架构决策

新增三条 ADR，见 [ARCHITECTURE.md](ARCHITECTURE.md)：

- **ADR-11**：蓝图结构由代码计算，不由模型规划
- **ADR-12**：声纹提取而非原文搬运
- **ADR-13**：深度必须逐维度参数化，不能是形容词
